## 1. 一页项目卡片（必须背下来）

### 1.1 30 秒版

> 这是一个可配置、可评测、可溯源的多 Agent 行业调研系统。我参考 CrewAI 的 Agent/Task 抽象自研了轻量 DAG 编排内核，把研究员、分析师、撰写员三个角色串成“研究规划 → 联网检索 ∥ 私有研报检索 → 证据合并 → 结构化分析 → 分章节成稿”的闭环。核心不是“让 LLM 写一篇”，而是让每条结论都有证据编号、每个阶段都可观测、效果可用指标验证。接入 6 份公开研报、992 页、1896 个切片，使用 GLM embedding-3 并加公司/年份元数据过滤后，100 题评测检索命中率 97%、MRR 0.8889；GLM 配置下闭卷 14% → RAG 90%，Hashing + DeepSeek 基线为 16% → 88%；端到端 DeepSeek 配置约 3 分钟、26 万 token、成本约 5 美分。

### 1.2 2 分钟版（结构：痛点 → 方案 → 难点 → 结果 → 反思）

1. **痛点**：行业调研资料分散、报告周期长；直接用 LLM 写，事实不可溯源、无法评测。
2. **方案**：四层架构（接入 / 编排 / Agent 运行时 / 能力层）；DAG 任务图；角色、任务、工具权限全部 YAML 化；证据包作为唯一事实源。
3. **难点**：让 LLM 在长上下文、严格 Schema、引用约束下稳定交付；我做了 JSON 三层抽取 + Pydantic 校验 + 纠错重试 + 截断检测 + 空证据闸门。
4. **结果**：6 份研报 / 992 页 / 1896 切片；GLM embedding-3 + `company/report_year` 过滤后，100 题 Top-8 检索命中率 97%、MRR 0.8889（题库共 501 题，当前对照取前 100 题）；GLM 配置闭卷 14% → RAG 90%（95% CI 82.6%–94.5%），Hashing + DeepSeek 基线 16% → 88%；端到端（DeepSeek 配置）178.5 秒、264k token、$0.05。
5. **反思**：文本 ReAct 协议对格式敏感、评测集与语料同源、**题目未点名公司导致跨公司混淆**——这三点是我下一步会优先改造的。

## 3. 核心问答（按面试官提问顺序）

### 第一层：动机与整体设计

**Q1. 为什么做这个项目？解决什么问题？**

- 三个痛点：资料分散、报告周期长、LLM 直写不可溯源。
- 目标不是“一键生成”，而是“**每个结论有证据、每个阶段可观测、效果可评测**”。
- 所以系统里最重要的设计不是 Prompt，而是 **EvidenceBundle + OutputContract + RunTracker** 三件套。

**Q2. 整体架构讲一下。**

四层：

1. 接入层：CLI / Streamlit，只做参数与展示；
2. 编排层：`ResearchPipeline` → `Crew`（DAG）→ `Agent`（Direct/ReAct/long_form）；
3. 能力层：LLM、Search、Fetch、KnowledgeBase、Renderer；
4. 配置层：`settings.yaml` / `agents.yaml` / `tasks.yaml`。

数据流：`plan → (collect_web ∥ collect_kb) → merge_evidence → analyze → write`。

**Q3. 为什么用 DAG，不用顺序链？**

- 联网检索与私有研报检索互不依赖，可以并行，端到端省掉一段串行时间；
- DAG 能表达“失败只阻断下游、不阻断无关分支”；
- 顺序链在写作阶段会把所有上下文塞进一次调用，容易截断；DAG 让每个任务有独立上下文与交付契约。

**Q4. 为什么自研，不用 CrewAI / LangGraph？**

- CrewAI 的 Process 以顺序/层级为主，DAG 并行、失败隔离、任务级 Schema 校验、工具权限、事件粒度都不够可控；
- LangGraph 很通用，但我们要的是“配置驱动 + 契约校验 + 证据链”的窄场景，引入图状态管理反而增加复杂度；
- 自研核心约 670 行（`agent.py` 481 行 + `crew.py` 189 行），换来完全可控的调度与观测；
- 代价：生态、可视化、持久化要自己补。如果团队已有 LangGraph 基建，我会优先复用而不是重写。

**Q5. 这算真正的多 Agent 吗？**

坦率说：是**角色化多 Agent 工作流**，不是自主协商式多 Agent。

- 三个角色有独立 system prompt、工具白名单、上下文和交付契约；
- 编排是确定性 DAG，自主性只体现在研究员的 ReAct 检索循环和 Coverage 补搜；
- 这样设计是因为报告场景对可靠性和成本更敏感，全自主协商收益低、调试难。
- 如果要做自主协商，需要共享黑板、消息总线、角色间辩论/投票，以及更强的终止条件——这是另一种取舍。

**Q6. Agent 之间怎么通信？**

- 不共享记忆、不互发消息；
- 上游 `TaskResult.text` 作为下游 prompt 的依赖段落，`parsed` 作为结构化输入；
- 证据通过 `EvidenceBundle` 单一事实源传递；
- 优点：简单、可复现、易定位；缺点：上下文膨胀，依赖文本超过 `max_dep_chars=20000` 会被截断。
- 改进方向：产物落 artifact，下游按 ID/摘要引用；或引入共享黑板 + 分层摘要。

### 第二层：编排与 Agent 运行时

**Q7. Crew 的调度算法讲一下。**

每一轮：

1. `blocked`：任一依赖失败 → 标记跳过并移除；
2. `ready`：所有依赖完成 → 并行（`ThreadPoolExecutor`，`max_workers=2`）或串行；
3. 如果既没有 ready 也没有 blocked → 依赖图不可满足，剩余任务全部报错退出；
4. 单任务异常：任务级重试（默认 1 次），仍失败则写入 `errors`，不影响同轮其他任务。

环检测用三色 DFS（白/灰/黑），发现灰色节点即环，输出 `a -> b -> a` 路径。

**Q8. 失败隔离具体怎么体现？**

- `collect_web` 失败，只阻断 `merge_evidence → analyze → write`；`collect_kb` 仍会执行完；
- 反过来也一样；
- 但 `merge_evidence` 是硬闸门：两路都没有证据时直接抛 `EvidenceUnavailableError`，Runner 转 `PipelineError`，不允许生成无来源报告；
- `write` 失败则整个 run 失败；其他非关键任务失败只会让状态变成 `partial`。

**Q9. 重试有几层？会不会重复计费？**

两层：

- **校验重试**（Agent 内）：输出不合规 → 纠错 prompt → 最多 2 次；
- **任务重试**（Crew 级）：整个 Agent 重跑，默认 1 次。

任务级重试确实会重复 LLM 调用和工具调用，不保证幂等。改进：工具幂等 + 结果缓存 + checkpoint；当前场景可接受，因为重试是低频异常路径。

**Q10. ReAct 循环怎么实现？停止条件是什么？**

- 文本协议：`Thought` / `Action` / `Action Input` / `Observation` / `Final Answer`；
- `Action` 必须独占一行，`Action Input` 是 JSON；只有一个必填参数时允许直接传字符串；
- 每步执行工具，Observation 超过 3000 字截断；
- 停止条件：命中 `Final Answer` 并通过校验；或达到 `max_steps = min(角色 7, 全局 7)`；
- 达到上限后进入“强制交付”阶段，要求模型基于已有 Observation 直接输出，再给最多 2 次校验机会。

**Q11. 模型不按 ReAct 格式输出怎么办？**

- 解析失败时，这一步既没有 Action 也没有 Final，就当作“模型直接给了答案”，走校验；
- 校验失败 → 纠错 prompt；
- 工具失败不抛异常，返回 `ERROR: ...` 作为 Observation，让模型自愈；
- 但我知道这不是最优解：更稳的是原生 `tool_calls` / Function Calling，文本协议只做 fallback。

**Q12. 工具权限怎么做的？为什么放在运行时？**

```python
allowed = set(spec.tools)
if task.tools is not None:
    allowed &= set(task.tools)
```

- `tasks.yaml` 里 `tools: []` 表示禁用该任务全部工具；
- `registry.execute(..., allowed=allowed)` 会再次校验，并丢弃 Schema 未声明的参数；
- 放在运行时而不是只写在 Prompt 里，是因为 Prompt 约束可被绕过，运行时校验才是真正的边界。

**Q13. Observation 为什么要截断到 3000 字？**

- 防止一次工具返回把上下文打爆；
- 3000 字足够包含标题、URL、摘要和关键数字；
- 代价：可能截掉长网页里的关键段落 → 所以研究员会先 `search_web` 再 `fetch_page`，用摘要决定要不要抓全文。

**Q14. 结构化输出怎么保证稳定？**

四层：

1. **抽取**：代码围栏 → `raw_decode` 扫描 → 取最长候选，避免把 Prompt 里的示例当交付物；
2. **校验**：Pydantic；证据类 `extra="forbid"`；
3. **重试**：把校验错误 + 契约提示回喂模型；
4. **截断检测**：`finish_reason == "length"` 时直接判定不完整，注入压缩重述提示。

Markdown 任务则校验字数、必需章节、`[E#]` 去重数量、是否存在表格。

### 第三层：RAG 与评测

**Q15. RAG 全链路讲一下。**

解析（PDF 逐页 / DOCX 段落+表格转 Markdown）→ 清洗 → 递归切片 900/150 → Embedding（默认智谱 GLM `embedding-3`，2048 维；可切 OpenAI 或离线 Hashing）→ 本地 NumPy / Chroma → 查询时“向量 + 词法”混合打分 → 阈值过滤 → Top-K → 通过 `kb_search` 工具返回 JSON 给 Agent。

**Q16. 为什么用 GLM embedding-3？为什么还保留 Hashing？**

- GLM `embedding-3` 走智谱的 OpenAI 兼容接口，接入成本低，中文语义明显强于字符哈希；
- 2048 维、L2 归一化，直接兼容现有余弦检索；
- 实测同一批 100 题：Hashing 89% / MRR 0.8003 → GLM 93% / MRR 0.8201（原始题目），召回和排序都提升；
- 代价是每次查询多一次网络调用，单题检索从 ~11ms 升到 ~188ms；
- Hashing 保留为离线回退：`demo` 和单测不依赖 Key、确定性、零成本；
- 切换 Embedding 必须重建索引，`meta.json` 会拒绝 embedder 不匹配的旧索引。

**Q17. 混合检索的公式？为什么是 0.55/0.45？**

```python
lexical = |query_terms ∩ chunk_terms| / |query_terms|
score = 0.55 * max(0, vector_score) + 0.45 * lexical
```

- 词法项是中文 bigram/trigram + 英文单词 + 数字；
- 长研报里向量容易被主题词稀释，词法能把包含具体公司名/数字的切片拉回来；
- 0.55/0.45 是初始手调值，用评测集验证过 hit rate，但没有做大规模消融——这是可以改进的点：网格搜索权重，或用 RRF 做秩融合。

**Q18. 切片大小怎么定的？**

- 研报财务表格密集，切片太小会切断表格，太大又会稀释语义；
- 取 900 字 / 150 overlap，是“表格完整性”和“检索粒度”的折中；
- 通过评测观察：切片过小命中率下降，过大 MRR 下降；
- 更细的做法是按标题层级/表格边界做结构感知切片，目前没做。

**Q19. 检索评测怎么做的？**

- 只统计可回答题（不可回答题不参与检索命中率）；
- 对每个 `(top_k, threshold)` 组合逐题检索；
- 相关性判定优先级：`evidence_quote` 前缀（60/40/24 字）→ 答案关键词/别名 → source/page；
- 命中则 `hits += 1`，`MRR += 1/rank`；
- 结果：Top-8 / 阈值 0.15；GLM embedding-3 原始题目 100 题为 93% / 0.8201；补全公司/年份但不过滤为 88% / 0.7416；加 `company/report_year` 过滤后 100 题为 **97% / 0.8889**，平均 ~175ms；Hashing 基线为 89% / 0.8003 / 10.88ms。501 题是题库总量（493 可答 + 8 不可答），当前对照只取前 100 题，全量 501 的历史数字（97.16% / 0.884）不再引用。

**Q20. 闭卷 vs RAG 怎么测的？**

- 同模型、同题目、同答案匹配规则；
- 闭卷 Prompt 明确要求“给最可能答案，不要用无法确定代替作答”，避免用拒答拉低基线；
- RAG Prompt 要求“只根据给定资料回答，资料不足说无法确定”；
- 答案匹配：别名子串 + 数字集合交集；不可回答题看拒答标记；
- 结果：deepseek-chat + Hashing 为 16% → 88%（+72pp，CI 80.2%–93.0%）；GLM 配置 + GLM embedding-3 + 元数据过滤为 14% → 90%（+76pp，CI 82.6%–94.5%）；未过滤的历史 GLM 配置为 10% → 84%。三组不是同一模型/索引，不能直接横向比较。

**Q21. 97% 和 90%/88% 是不是自己出题自己考？**

这是这个项目最容易被挑战的点，必须主动承认并给出边界：

- 评测集确实由同一批语料生成（LLM grounded QA + 规则抽取 + 人工种子），存在**同源泄漏**；
- 但我做了低价值题过滤、证据可回溯校验、去重，保证题面与证据片段对应；
- 闭卷对照仍然有效，因为它证明“模型本身不知道这些公司级细节”；
- 局限：答案是词面/数字匹配，不是语义判分；样本只有 100 题；没有人审；
- **更严重的是题目歧义**：前 100 题全部来自埃斯顿年报，其中 96 题没有点名公司；四家年报的“研发投入/净利润/现金流”措辞几乎一样，检索很容易把别家公司的同名科目排到第 1；
- 改进：题目补全公司名 + 元数据过滤 + 单位归一化 + 人审 + held-out + 分层抽样覆盖 501 题题库。

**Q21.5 为什么曾出现 88→84，后来怎么回到 90%？**

先给结论：**88→84 不是公平的 Embedding A/B，84% 也不是真实退步；补全题目并加元数据过滤后，同一 GLM 配置回到 90%。** 证据链：

1. **模型也换了**：88% 那次是 `deepseek-chat` + Hashing；84% 那次是 GLM 配置 + GLM embedding-3；
2. **闭卷独立佐证**：闭卷从 16% 掉到 10%，闭卷不经过检索，说明模型/采样差异本身就存在；temperature=0.3 也有随机性；
3. **样本量**：100 题差 4 题，95% CI 分别 80.2–93.0 与 75.6–89.9，高度重叠，不构成显著下降；
4. **逐题对比**：8 题从对变错、4 题从错变对，净 -4；其中 2 题其实是判分误杀（`5.03 亿元` = `503,007,657.74 元`；q073 是语义正确的改写）；
5. **剩余 6 题是跨公司错配**：正确答案的切片都在 Top-8 里，但排在第 2–5；第 1 名是汇川/拓斯达/新时达的同名科目。例如：
   - `fin_q057`：第 1 名汇川 1,334,992,885.51，第 2 名埃斯顿 142,930,685.98，模型答了前者；
   - `fin_q026`：第 1 名汇川研发数据，第 2 名埃斯顿 503,007,657.74，模型答了 3,147,080,701.82；
   - `fin_q056`：正确切片排第 5，前 4 名是汇川/拓斯达的现金流科目。
6. **检索指标本身没有退步**：Top-8 命中 100%，Top-3 从 91% 升到 94%；但 Top-1 来源准确率只有 75%（Hashing 77%），而问答模型倾向于使用第 1 名。
7. **补全公司/年份后**：Top-1 来源准确率 75%→90%、Top-3 94%→98%，但切片级 hit@8 93%→88%、MRR 0.820→0.742；说明“查询里加公司名”能选对公司，却会稀释同一份年报内部的切片排序。
8. **最终方案**：入库写 `company/report_year` 元数据，检索先过滤候选，再用 `strip_report_context()` 去掉题干前缀，只用核心问题排序。100 题实测 **97% / MRR 0.8889**；问答从 84% 回到 **90%**（闭卷 14%，+76pp，CI 82.6%–94.5%）。剩余 10 题主要不是检索问题，而是表格行列错位、PDF 乱码和单位判分。

一句话回答面试官：**“88→84 不是 Embedding 的锅：模型也从 DeepSeek 换成了 GLM，闭卷同时从 16 掉到 10，4 题差异在 CI 噪声内。我没有继续调参，而是给切片加 company/report_year 元数据，检索先过滤再排序，hit@8 从 93% 提到 97%、MRR 0.889，问答回到 90%。剩下的错误集中在表格行列对齐和 PDF 乱码，是下一步做表格化切片和 OCR 的方向。”**

**Q22. 为什么只测 100 题，不是 501 题？**

- 501 题是题库总量（493 可答 + 8 不可答），当前评测只跑前 100 题，是快速对照子集；全量 501 的历史运行产物未保留；
- **但这 100 题有采样偏差**：`--limit 100` 取文件前 100 行，全部来自埃斯顿年报；完整集里还有拓斯达 122、汇川 116、新时达 107、IFR 25；
- 当时主要成本在问答评测的 LLM 调用；
- 更严谨的做法是按 source 分层抽样 100 题，或直接跑全量；
- 面试时不要把 100 题说成“全部评测集”，要主动说明这是子集且存在来源偏差。

**Q23. 索引和评测数字能复现吗？**

能：

```powershell
python -m app.cli bootstrap
python -m app.cli eval --qa-file data/eval/qa_robotics_v2.jsonl --top-k 8 --thresholds 0.15
```

- 检索评测不需要 LLM Key，但默认 Embedding 是 GLM，需要 `ZHIPU_API_KEY`；
- 产物在 `runs/eval_results.json`，Hashing 基线备份在 `runs/eval_results_hashing.json`；
- 索引快照差异：GLM 重建后 9 sources / 1896 chunks（含 3 份演示语料，仅 6 个切片）；Hashing 评测时 6 sources / 1890 chunks。
- 想复现离线基线：把 `rag.embedding` 临时改成 `hashing`、`dim: 768` 再重建。

**Q24. GLM Embedding 下，跨公司问题怎么处理？**

- 语义向量已经能区分“埃斯顿毛利率”和“汇川毛利率”这类表述，比 Hashing 明显改善；
- 但公司名、年份、具体数字仍主要靠词法项兜底；
- 剩余 miss 多来自表格跨页、指标口径不一致、切片边界；
- 生产方案：metadata 过滤（按 source/公司/年份）+ rerank，而不是只靠向量。

### 第四层：工程化、故障与反思

**Q25. 讲一个你排查过的最难的 bug。**

用 STAR：

- **S**：联网检索明明有结果，但系统提示“未获得任何可用证据”，报告生成失败。
- **T**：定位为什么证据包为空，并保证不再静默失败。
- **A**：复现后看 `events.jsonl`，发现研究员输出的 `EvidenceBundle` 超过 `max_tokens` 被截断；Schema 当时是 `extra="ignore"`，截断后的残缺 JSON 被静默接受，`items` 变成空列表，后续继续跑。
- **修复 7 项**：`finish_reason=length` 检测并重试、证据类改 `extra="forbid"`、合并后空证据直接报错、Prompt 限制证据条数与 detail 长度、工具返回压缩、写作引用下限动态化、补回归测试。
- **R**：单测全绿，离线 demo 恢复；更重要的是把“静默失败”变成了“显式失败”。

**Q26. 为什么 `extra="forbid"` 能解决这个问题？**

- `ignore` 会把未知字段丢掉，截断时缺失/错位字段不会报错；
- `forbid` 遇到未知字段直接校验失败，Agent 就会进入纠错重试；
- 再配合空证据闸门，保证“空包”不可能进入分析与写作。

**Q27. 成本怎么控制？**

- 研究员每轮证据 ≤8 条、detail ≤120 字；
- Observation ≤3000 字，依赖文本 ≤20000 字；
- 写作按章节生成，每节只带分析与证据的紧凑视图；
- 实测机器人行业：264k token、$0.05、37 次 LLM、21 次工具；
- 最直接的旋钮：`max_tokens`、`max_react_steps`、`max_coverage_rounds`、`target_chars`。

**Q28. 延迟瓶颈在哪？怎么优化？**

- `metrics.json` 的 `slowest_stages` / `by_agent`；
- 机器人 run：研究员约 107 秒，写作是主要剩余耗时；
- 已做：web/kb 并行、证据压缩、ReAct 步数上限；
- 可做：写作章节并行、流式输出、工具结果缓存、异步任务队列。

**Q29. 多用户/线上怎么办？**

当前是单机演示，明确缺口：

- Streamlit 无任务队列，多用户会互相阻塞；
- 无鉴权、无用户级 Key 隔离；
- 本地 NumPy 是 O(N) 暴力检索；
- 改进：FastAPI + 异步任务队列（Celery/RQ）、任务状态表、限流与配额、ANN 向量库、对象存储产物。

**Q30. 安全方面考虑了什么？**

- `calculator` 用 AST 白名单，禁止属性访问、下标、任意函数调用；
- 工具权限在运行时校验；
- API Key 只从环境变量读取，不落盘；
- 网页内容是**不可信输入**，存在 Prompt Injection 风险；
- 生产需要：URL 白名单、内容隔离/标记、输出审查、工具沙箱。

**Q31. 测试怎么做的？**

8 个测试文件、36 个测试函数：

- 协议解析（ReAct 格式、代码围栏 JSON）；
- 结构化校验（截断残包、未知字段、Markdown 契约）；
- DAG（顺序、并行、环检测、失败隔离）；
- 工具（计算器安全、权限、fixture 检索、正文抽取）；
- 切片（长度、overlap、非法参数）；
- RAG（入库、检索、阈值、持久化、增量去重）；
- 评测（数值/别名匹配、拒答、CI、规则构建器）；
- 端到端 Mock（报告长度、引用、章节、指标、HTML）。

缺口：没有真实 LLM 集成测试（成本与不稳定性），用 MockLLM 做协议级验证。

**Q32. 如果重做，你会改什么？**

按优先级：

1. 原生 Function Calling / 结构化输出，替换文本 ReAct 解析；
2. 证据用 artifact store，按 ID 引用，减少上下文传递；
3. 真实 Embedding + metadata 过滤 + rerank + RRF；
4. 评测人审 + held-out + LLM judge + 分层覆盖 501 题题库；
5. 异步任务队列 + 章节并行 + 流式输出；
6. 更细的 Coverage 规则（每子问题证据数、来源多样性、时效性）。

## 5. 白板与手撕准备

### 5.1 手写 DAG 调度（伪代码）

```python
def run(tasks):
    pending = {t.id: t for t in tasks}
    results, errors = {}, {}
    while pending:
        blocked = [t for t in pending.values()
                   if any(dep in errors for dep in t.depends_on)]
        for t in blocked:
            errors[t.id] = "upstream failed"
        ready = [t for t in pending.values()
                 if all(dep in results for dep in t.depends_on)]
        if not ready:
            for t in pending:
                errors[t.id] = "dependency graph unsatisfiable"
            break
        run_parallel_or_serial(ready)   # 异常写入 errors
        pending = {k: v for k, v in pending.items()
                   if k not in executed and k not in blocked}
```

要能补充：环检测三色 DFS、`max_workers`、任务级重试。

```
build messages → loop:
  response = llm.chat()
  if finish_reason == length: inject compression hint
  elif Final Answer: validate → ok? return : correction
  elif Action: permission → execute → append Observation
  else: validate as final
  if steps >= max: force finalize
```
